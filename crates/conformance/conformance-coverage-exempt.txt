# The Singer target bridge forwards `key_properties` and `ACTIVATE_VERSION` to an
# external target: whether rows converge by key, or stay hidden until the
# version is activated, is that target's behaviour, not the bridge's. The sink
# declares neither keyed_upsert nor keyed dedup for that reason.
faucet-sink-singer keyed_write_modes: upsert passes key_properties to an external target; convergence is the target's, which the bridge cannot vouch for (it declares no keyed_upsert)
faucet-sink-singer overwrite: ACTIVATE_VERSION makes the target drop older versions at commit; rows of the new version are visible as the target loads them, so staging is the target's

# Warehouse sinks without an emulator are tested against a wiremock fake of
# their statements API. The fake applies appends and keeps the watermark, which
# proves the sink's side of exactly-once and per-row outcomes; key
# convergence, MERGE and INSERT OVERWRITE semantics are the warehouse's own, so
# a fake would only test itself. Their SQL is pinned by the src/sql.rs unit
# tests instead.
faucet-sink-databricks keyed_write_modes: MERGE semantics are the warehouse's (no emulator); the MERGE text is pinned by src/sql.rs unit tests and the fake-warehouse tests in tests/integration.rs
faucet-sink-databricks replay_safe: a replayed keyed write is a MERGE, which converges by the warehouse's key semantics (no emulator); pinned by the upsert tests in tests/integration.rs
faucet-sink-databricks overwrite: staging and INSERT OVERWRITE run in the warehouse (no emulator); the lifecycle statements are pinned by tests/integration.rs
faucet-sink-bigquery keyed_write_modes: MERGE semantics are BigQuery's (no emulator runs the MERGE script); the script is pinned by src/merge.rs unit tests and tests/upsert.rs
faucet-sink-bigquery replay_safe: a replayed keyed write is one MERGE, which converges by BigQuery's key semantics (no emulator); pinned by src/merge.rs unit tests and tests/upsert.rs
faucet-sink-bigquery overwrite: the temp-table load and TRUNCATE + INSERT swap run in BigQuery (no emulator); the lifecycle requests are pinned by tests/overwrite.rs
faucet-sink-redshift atomic_batches: batches are atomic only for write_strategy: copy with batch_size: 0, whose COPY FROM 's3://…' needs a real cluster and bucket; COPY SQL is unit-tested in src/copy.rs

# Proven by #[ignore]d tests that need a SQL Server with CDC enabled; the
# nightly integration-heavy workflow runs them with --include-ignored.
faucet-source-mssql-cdc exactly_once: assert_bookmark_roundtrip runs in an #[ignore]d test (needs SQL Server CDC); run nightly by integration-heavy.yml

# Check 22 (`streaming`) needs a count of the records the backend has served
# when the first page arrives. The HTTP-backed sources prove it against a
# counting wiremock fake (rest, elasticsearch, bigquery, snowflake,
# databricks). For the sources below no such count is observable in CI: the
# backend streams through a driver, broker client, store client or child
# process that exposes no served-record counter, so check 2
# (`assert_bounded_memory`) is the evidence there.
faucet-source-clickhouse streaming: rows arrive through the clickhouse client's streaming cursor; the test server exposes no served-row count
faucet-source-duckdb streaming: an embedded engine in the same process; there is no separate backend whose served rows can be counted
faucet-source-mongodb streaming: documents arrive through the driver's cursor batches; the test server exposes no served-document count
faucet-source-mssql streaming: rows arrive through the TDS row stream; the test server exposes no served-row count
faucet-source-mysql streaming: rows arrive through the sqlx row stream; the test server exposes no served-row count
faucet-source-oracle streaming: rows arrive through ODPI-C fetch batches; the test server exposes no served-row count
faucet-source-postgres streaming: rows arrive through the sqlx row stream; the test server exposes no served-row count
faucet-source-redshift streaming: rows arrive through the Postgres-wire row stream; the test server exposes no served-row count
faucet-source-spanner streaming: rows arrive through ExecuteStreamingSql on the emulator, which exposes no served-row count
faucet-source-sqlite streaming: an embedded database file read in-process; no separate backend whose served rows can be counted
faucet-source-mongodb-cdc streaming: a change stream has no end of result set to be served before the first page
faucet-source-mssql-cdc streaming: CDC polling has no end of result set to be served before the first page
faucet-source-mysql-cdc streaming: a binlog stream has no end of result set to be served before the first page
faucet-source-oracle-cdc streaming: LogMiner reads have no end of result set to be served before the first page
faucet-source-postgres-cdc streaming: a replication stream has no end of result set to be served before the first page
faucet-source-kafka streaming: a broker log read until idle has no end of result set to be served before the first page
faucet-source-kinesis streaming: a shard stream read until idle has no end of result set to be served before the first page
faucet-source-nats streaming: a subject read until idle has no end of result set to be served before the first page
faucet-source-pubsub streaming: a subscription read until idle has no end of result set to be served before the first page
faucet-source-rabbitmq streaming: a queue read until idle has no end of result set to be served before the first page
faucet-source-redis streaming: stream/list/key reads go through the redis client, which exposes no served-entry count
faucet-source-sqs streaming: a queue read until idle has no end of result set to be served before the first page
faucet-source-dynamodb streaming: the conformance tests run against DynamoDB Local, which exposes no served-item count

faucet-source-gcs streaming: objects are read through the storage client from fake-gcs-server, which exposes no served-byte count

faucet-source-file streaming: local files are read directly; there is no backend whose served records can be counted
faucet-source-csv streaming: local files are read directly; there is no backend whose served records can be counted
faucet-source-parquet streaming: row groups are read through object_store from local files or S3, which exposes no served-row count
faucet-source-delta streaming: table files are read through deltalake's object store, which exposes no served-row count
faucet-source-iceberg streaming: data files are read through the iceberg FileIO, which exposes no served-row count
faucet-source-grpc streaming: messages arrive through a tonic server stream from the test server, which counts nothing
faucet-source-singer streaming: records come from a child process's stdout, which exposes no served-record count
